# Cordn Nostr-Shaped Message Envelopes

- Status: Draft

## Abstract

This document defines the `cordn` application-message envelope model. It specifies a Nostr-shaped message envelope carried inside MLS application messages so implementations can reuse Nostr event structure, `kind` values, tags, and event identifiers without requiring Nostr signatures. In `cordn`, authorship is established by MLS authenticated sender identity and the stable identity binding defined in [`spec/00.md`](spec/00.md).

## Specification

### 1. Overview

`cordn` messages MUST use a Nostr-shaped message envelope as application payload.

- The envelope is carried inside an MLS application message.
- The envelope is intentionally unsigned.
- The envelope uses Nostr event field conventions for application semantics.
- The envelope `id` is derived using Nostr NIP-01 event serialization conventions.
- The envelope `pubkey` is bound to MLS sender identity rather than to a Nostr signature.

This model allows `cordn` implementations to reuse familiar Nostr message structure while keeping authentication and privacy properties rooted in MLS and the coordinator identity model.

### 2. Envelope Fields

The message envelope MUST follow the NIP-01 event field model for `id`, `pubkey`, `created_at`, `kind`, `tags`, and `content`.

The message envelope is a JSON object encoded as UTF-8.

The envelope MUST include those fields and MUST NOT include a `sig` field.

### 3. Encoding

The MLS application payload for a `cordn` message envelope MUST be the UTF-8 encoding of the envelope JSON object.

Implementations MUST preserve the semantic values of all envelope fields when encoding and decoding.

### 4. Event Identifier

The envelope `id` MUST be derived from the unsigned envelope using Nostr NIP-01 event serialization conventions.

Receivers MUST recompute the expected `id` from the received envelope fields and MUST reject the envelope if the recomputed identifier does not match the transmitted `id`.

The `id` is the canonical identifier for message references and application-level message identity.

### 5. Authorship and Identity Binding

The envelope is not self-authenticating.

Instead, authorship is established by:

- MLS authenticated sender identity for the enclosing application message
- the stable public-key identity bound to that sender credential as defined in [`spec/00.md`](spec/00.md)

The envelope `pubkey` MUST equal the authenticated sender identity derived from the sender’s MLS credential.

Receivers MUST reject an envelope whose `pubkey` does not match the authenticated sender identity of the enclosing MLS application message.

### 6. `kind` and Tag Conventions

Implementations SHOULD reuse Nostr `kind` values and tag conventions when their semantics match the intended `cordn` application behavior.

Examples include:

- `kind: 9` for chat messages, following [NIP-C7](https://github.com/nostr-protocol/nips/blob/master/C7.md)
- `kind: 1111` for threaded replies, following [NIP-22](https://github.com/nostr-protocol/nips/blob/master/22.md)
- `kind: 7` for reactions, following [NIP-25](https://github.com/nostr-protocol/nips/blob/master/25.md)

There is no required set of `kind` values for `cordn` implementations. These are basic chat-style message conventions only. Implementations MAY use conventions from other NIPs when appropriate.

For threaded replies, `cordn` implementations SHOULD follow NIP-22 comment conventions rather than the reply convention described in NIP-C7.

Tags SHOULD be used for replies, reactions, threading, and other message relationships according to the applicable NIP conventions.

This document does not require support for any specific `kind` value or tag convention beyond preserving them as part of the envelope.

### 7. Message References

When a `cordn` message refers to another message, implementations SHOULD use the referenced envelope `id`.

Coordinator cursors defined in [`spec/00.md`](spec/00.md) are delivery-order primitives and are not canonical message identifiers.

### 8. Interoperability Requirements

Implementations MUST agree on all of the following:

- UTF-8 JSON encoding of the envelope object
- absence of the `sig` field
- use of NIP-01 event serialization conventions for `id` derivation
- equality between envelope `pubkey` and MLS-authenticated sender identity

### 9. Rationale

This model is intentionally simple.

- Nostr-shaped envelopes provide a familiar and expressive application message structure.
- Omitting signatures avoids extra signer usage, and redundant author proof because `cordn` already authenticates authorship through KeyPackage identity binding and MLS sender authentication.
- Reusing NIP-01 event identifier conventions provides stable message identifiers without introducing a `cordn`-specific event-id scheme.
- Using envelope `id` for references cleanly separates application message identity from coordinator delivery cursors.

This approach keeps `cordn` message semantics compact, expressive, and aligned with the rest of the protocol model.
