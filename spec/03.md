# Cordn Opaque Group Payloads

- Status: Draft

## Abstract

This document defines the `cordn` group-payload delivery model. Coordinators store and serve group messages as opaque bytes and do not parse, decode, or validate message content. Clients seal payloads with a per-epoch key derived from the MLS exporter so that only group members can read them.

This document also defines the delivery group identifier (`gid`), the sealed payload wire format, the MLS exporter parameters used for content protection. The cursor model defined in [`spec/00.md`](spec/00.md) is unchanged; this document constrains only how message content is shaped and protected.

## Specification

### 1. Overview

`cordn` group messages are delivered as opaque, sealed payloads.

- Coordinators store and serve ordered message streams keyed by a delivery group identifier.
- Coordinators treat message content as opaque bytes.
- Payloads are sealed end-to-end between group members; only members able to derive the relevant epoch key can read them.
- Content protection is entirely a client concern; the coordinator gains no visibility into message content.

This document defines only the payload delivery and protection model. Coordinator roles, identity binding, and cursor semantics are defined in [`spec/00.md`](spec/00.md). Application message envelopes are defined in [`spec/02.md`](spec/02.md).

### 2. Delivery Group Identifier

Each ordered message stream is identified by a delivery group identifier (`gid`).

- `gid` names the delivery stream and its per-group cursor space. It is the value used for posting, fetching, and subscribing to group messages.
- `gid` is a delivery primitive. It is not the MLS `group_id`, and the coordinator MUST NOT assume any relationship between `gid` and any MLS group identifier.
- `gid` is opaque to the coordinator. The coordinator uses it only for stream identification, ordering, and fetch progression.
- Clients MAY derive `gid` from MLS group state, but any such derivation is a client convention and is not interpreted by the coordinator.

### 3. Payload Opaqueness

The coordinator treats message content as opaque.

- The coordinator MUST treat the message payload bytes as opaque.
- The coordinator MUST NOT parse, decode, or validate message content.
- The coordinator MUST NOT derive MLS state from message content.
- The coordinator provides ordered storage and delivery keyed by `gid`. Content interpretation is exclusively a client responsibility.

### 4. Sealed Payload Format

Group message payloads are sealed with a per-epoch key derived from the MLS exporter.

The encryption key MUST be derived using the MLS Exporter with the following parameters:

- secret: the exporter secret of the relevant MLS epoch, as defined by the MLS key schedule
- label: `"cordn"`
- context: the UTF-8 encoding of `"group-payload"`
- length: `32` bytes

The sealed payload MUST use `ChaCha20-Poly1305` as the AEAD.

In TLS notation:

```tls
opaque Nonce[12];
opaque Ciphertext<..>;   // AEAD ciphertext and 16-byte authentication tag

struct {
    Nonce nonce;
    Ciphertext ciphertext;
} SealedPayload;
```

Requirements:

- The nonce MUST be exactly 12 bytes, freshly generated at random for each sealed payload, and MUST NOT be reused with the same key.
- The AEAD associated data MUST be the empty byte sequence.
- The message payload field MUST carry the standard base64 encoding (with padding) of the serialized `SealedPayload`.
- A valid `SealedPayload` is at least 28 bytes: a 12-byte nonce plus a 16-byte authentication tag.
- Only members able to derive the epoch's exporter secret can decrypt. The key rotates automatically with each MLS epoch advance.

### 5. Epoch Selection

Each sealed payload is encrypted under the exporter secret of a specific MLS epoch. Implementations MUST select the epoch as follows.

- Application messages MUST be sealed under the exporter secret of the sender's current epoch.
- Commits MUST be sealed under the exporter secret of the epoch the Commit transitions from. This ensures that all members still in that epoch can decrypt the Commit before advancing their state.

### 6. Sender Authentication

Because payloads are sealed, the coordinator cannot establish authorship of message content.

- Authorship is established by recipients, after decryption, through MLS authenticated sender identity as defined in [`spec/00.md`](spec/00.md) and the envelope binding defined in [`spec/02.md`](spec/02.md).
- The coordinator's role is limited to ordered delivery; it gains no visibility into message authors or content.

### 7. Interoperability Requirements

Implementations MUST agree on all of the following:

- the MLS Exporter parameters: label `"cordn"`, context `"group-payload"`, length `32`
- the AEAD algorithm (`ChaCha20-Poly1305`), nonce length (12 bytes), nonce uniqueness rules, and empty associated data
- the sealed payload wire layout and base64 encoding
- the meaning of `gid` as a delivery primitive distinct from MLS `group_id`
- the epoch selection rules for sealing Commits

Implementations MUST reject sealed payloads that are malformed, shorter than the minimum valid length, or that fail AEAD verification.

### 8. Rationale

This model is intentionally minimal and keeps trust concentrated in MLS rather than in the coordinator.

- Payload opaqueness minimizes coordinator trust: the coordinator cannot read, classify, or validate message content.
- Deriving content-protection keys from the MLS exporter requires no extra key exchange, and key rotation comes for free from MLS epoch advances.
- Sealing Commits under the pre-Commit epoch secret keeps membership changes readable by every current member without out-of-band negotiation.
- Decoupling `gid` from MLS `group_id` keeps delivery a pure coordinator concern and leaves group-state semantics to clients.

This approach keeps the `cordn` delivery model uniform and coordinator-light while preserving end-to-end confidentiality between group members.
